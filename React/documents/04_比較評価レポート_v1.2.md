## 1. 評価の前提（必読）

### 1.1 自己評価バイアス
本レポートの評価者（Claude Fable 5）は fable版の実装者と同一モデルであり、**利益相反がある**。対策として、すべての優劣判定に根拠（ファイルパス・行番号・コマンド出力）を付し、根拠を示せない判定は記載していない。

### 1.2 入力条件の非対称性（git履歴で確認済み）
- 自作版は設計書が**進化する過程で**実装された。画面設計書v2.0は自作版の実装に合わせて整合された（コミット `c76a156`, 2026-06-08）。
- fable版はその**整合済み設計書**を入力として実装された（`95d03b9`, 2026-06-12）。
- つまり fable版は「自作版の実装経験が反映された設計書」を使えた点で有利。「設計書への忠実度」の比較はこの前提付きで読むこと。

### 1.3 評価方法の限界
- 判定は**コード読解＋静的解析**（`tsc --noEmit` / ESLint）に基づく。Supabase接続環境が必要なため、実行時の動作確認は行っていない。
- RLS（Row Level Security）は、fable版は `supabase/schema.sql` から検証可能だが、自作版はSQLがリポジトリに含まれないため「**検証不能**」として扱う。Supabase側に適切なRLSが設定されている可能性はあり、RLS自体の欠陥とは断定しない。

### 4.1 アーキテクチャ — 自作 3 / fable 4

- **自作版**: 全ページ `'use client'` で、認証・認可ガードもクライアント側レイアウト（`(user)/layout.tsx`, `admin/layout.tsx`）に集約。ガードの集約自体は良い設計（コミット履歴のリファクタリングの成果）だが、**サーバー側の防御層がない**。App Routerを使いながらServer Componentの利点（サーバー側認可・初期データ取得）を活かせていない。
- **fable版**: Server Component（page.tsx）で認証・認可・モジュール有効性を検査してからClient Componentに委譲する一貫した分離。`proxy.ts`（Next.js 16のmiddleware）+ Server Component + RLS の3層。減点は、独立API層を持たずクライアントから直接DB操作する構成が大規模化で制約になる点（ただしRLS前提のSupabase標準構成であり設計判断の範囲内）。

### 4.2 セキュリティ — 自作 2 / fable 4

- **自作版が2の理由**（明確な欠陥）:
  1. 認可の実効性が**リポジトリ内で検証不能**。データ保護はSupabase側のRLSに全面依存するが、そのRLS定義がリポジトリにない。実務では「インフラ設定が再現不能」自体が欠陥。
  2. 多層防御の欠如。予約の更新・キャンセルのクエリに `user_id` 条件がなく（`(user)/reservations/page.tsx`）、UIの出し分け（541行）だけが頼り。RLSが正しくなければ他人の予約を操作できる。
  - 良い点: 予約insertの `user_id` はセッション由来（フォーム由来でない）、Supabaseクエリビルダ使用でSQLインジェクションリスクなし、`.env.local` はgitignore済み。
- **fable版が4の理由**: 全5テーブルでRLS有効化に加え、設計書にない3件の穴を自主的に補正し記録している（`supabase/schema.sql`）:
  1. 未ログインanonキーでの全ユーザーメール読み取りを遮断（SELECTを `TO authenticated` に限定）
  2. admin用UPDATEポリシー追加（`reservations_update_admin`, 240-242行）
  3. **role自己昇格の防止**（`profiles_update_own` の `WITH CHECK` で role固定, 193-196行）— API直叩きで自分をadminに昇格する攻撃を封じる
  - さらに SECURITY DEFINER 関数の `search_path = ''` 固定（147-151行）、認証Cookieのキャッシュ対策も実装。
  - 減点: 重複防止のDB制約（`EXCLUDE USING gist`）がコメントアウトで任意扱い（288-303行）→ 完全同時送信のレースコンディションが理論上残る（README「既知の制約」に記録済み）。サーバー側の入力再検証もない。

### 4.3 コード品質 — 自作 3 / fable 4

- **自作版の良い点**: パターンの一貫性が高い。`refreshKey` / `isLoading` + `try/finally` / `isSubmitting`（多重送信防止）/ `BUTTON_*` 定数化が全ページで統一され、CLAUDE.mdの規約が実際に守られている。復元時の重複チェック（`admin/reservations/page.tsx:316-337`）も丁寧。
- **自作版の問題点**:
  - **実バグ**: `src/lib/utils.ts:17` の `formatTime` が時刻整形に `toLocaleDateString` を使用。実測出力は `2026/7/3 09:30` と**日付込み**になる。ダッシュボードの「開始 - 終了」表示（`(user)/dashboard/page.tsx:110`）では「2026/7/3 09:00 - 2026/7/3 10:00」と日付が重複表示される。`toLocaleTimeString` なら「09:00 - 10:00」。
  - 予約ロジック（バリデーション→重複チェック→insert/update）が `(user)/reservations` と `admin/reservations` でほぼ同一の重複コード。CLAUDE.md自身の「2ファイル以上で使う→lib/へ」の規約に違反。
  - リポジトリの雑然物: 空ファイル `{`（0バイト）、`CLAUDE.md` と `Claude.md` の重複併存（内容にも差分あり。大文字小文字を区別しないFSでは衝突する）。
- **fable版の良い点**: `types/database.ts` のDB型を全Supabaseクライアントにジェネリクス注入、`lib/datetime.ts` でJST固定計算を一元化し `new Date("YYYY-MM-DD")` 禁止方針までコメント化、境界条件（半開区間 `[start, end)`）の明示、定員減少エッジケースへの対応（`ReservationModal.tsx:66-67`）。
- **fable版の問題点**: `alert()`/`confirm()` と `Toast` の通知手段が混在（`ReservationManager` だけでalertが10箇所超）。697行の `ReservationManager.tsx` に4モードが同居。

### 4.4 保守性 — 自作 3 / fable 4

- **自作版**: `lib/` が合計100行未満の薄いユーティリティで、ドメインロジックが各ページに埋没・重複。最大763行のページコンポーネントはモーダル・フォーム・テーブルが未分割。状態管理はローカル `useState` のみで施設一覧等を各ページで個別フェッチ。
- **fable版**: `lib/reservations.ts`（重複判定）・`lib/datetime.ts`・`lib/modules.ts` にドメインロジックを集約し、`components/ui/`（Button/Modal/Toast/StatusBadge/Loading、各40〜50行）を再利用。減点は `ReservationManager.tsx`（697行）・`FacilityManager.tsx`（518行）の肥大と、フォームJSXの重複。全予約をクライアントで取得・フィルタする構成も数千件規模で問題化（README記録済み）。

### 4.5 ドキュメント — 自作 2 / fable 5

- **自作版**: `README.md` が **create-next-app のテンプレートのまま**。セットアップ手順・スキーマ・環境変数の説明が一切なく、第三者（未来の自分を含む）が環境再現できない。`CLAUDE.md` は開発規約・学習方針として非常に充実しているが、それはプロセスの文書であり、システムの文書ではない。
- **fable版**: README（143行）に技術スタック・画面一覧・Supabaseセットアップ手順（スキーマ適用〜developer昇格SQL）・**手動動作確認チェックリスト20項目**・**設計判断メモ9項目**・**既知の制約4項目**を網羅。実装の意思決定が完全にトレース可能で、実務のREADMEとしても上位水準。

### 4.6 テスト — 自作 1 / fable 1

**両者とも自動テストがゼロ**（`*.test.*` なし、テストフレームワーク未導入）。これは共通の最大の弱点。

- 自作版は CLAUDE.md の開発規約と `/review` コマンド（`.claude/commands/review.md`）による手動レビュー運用でカバーし、コミット履歴にも指摘修正の積み重ねがある（例: `565cb60`）。なお v1.1 まで本節が根拠としていた「5ラウンドのレビューループ」（`5c320e0`）は、`git show --stat` で確認したところ**変更対象がすべて fable-projects 配下**であり、fable版の修正過程だった（v1.2で帰属を訂正。§7と整合）。
- fable版はREADMEの動作確認チェックリスト（境界接触・復元中止・RLS確認等の重要ケースを網羅）と、実装直後の5ラウンドのレビューループ（`5c320e0`）でカバー。
- どちらも「何を確認すべきか」は持っているが、回帰を機械的に検出する手段がない。特に重複判定・日時変換のような純粋関数はテスト容易なだけに惜しい。
- 本観点でスコア1とする基準（アンカー）: 「自動テストが1件も存在しない」ことを§1.4の「1: 要件未達」に固定的に対応させる。手動チェックリストやレビュー運用はプロセスの評価（§4.3〜4.5）で扱い、本観点では加点しない。

### 4.7 設計書への忠実度と逸脱の扱い — 自作 3 / fable 4

評価軸は「逸脱の有無」ではなく「**逸脱を記録しているか**」（黙って逸脱すると後から仕様か手抜きか判別できなくなる）。

- **自作版**: モバイルのリスト表示（画面設計書 U-02）・人数上限バリデーション・モジュール実制御が未実装だが、**どこにも記録がない**。ただし §1.2 の通り、設計書側が自作版に合わせて更新された経緯があり、「実装しながら設計書を直す」進め方自体は学習プロセスとして妥当。
- **fable版**: 週/月カレンダー・`time_unit`・パスワードリセット等の未実装/簡略化を README「未実装（意図的にスコープ外）」に列挙し、設計書の不整合への補正は「設計判断メモ」に理由付きで記録。減点は逸脱そのものが残っている点（物理削除、DB制約の任意化）。

## 5. 総合評価と講評

**結論: fable版が7観点中6観点で上回り、特にセキュリティ（RLS設計）とドキュメントで差が大きい。ただし自作版は「学習者がヒントのみで自力実装した」という前提では高水準であり、静的品質ゲート（tsc/ESLint）と重複チェックの丁寧さでは互角。**

## 6. 学びポイント（自作版に取り込むべきfableの手法）

優先度順。上3つだけでも効果が大きい。

1. **DBスキーマをリポジトリに同梱する**（最優先）
   `fable-projects/supabase/schema.sql` の形式を参考に、現在のSupabase設定（テーブル・RLS・トリガー）をSQLとしてエクスポートしてコミットする。これだけで「認可が検証不能」という §4.2 の最大の問題が解消し、環境再現も可能になる。
2. **日時処理の一元化**
   `formatTime` バグ（`src/lib/utils.ts:17`）は個別の書き間違いではなく「日時処理が散在している」ことの症状。`fable-projects/lib/datetime.ts` のように日時ユーティリティを1ファイルに集約し、直接 `toLocale*` を呼ばない規約にする。
3. **多層防御**: RLSを信頼しつつ、更新・削除クエリにも `.eq('user_id', userId)` を付ける。1行の追加でRLS設定ミス時の被害を防げる。
4. **READMEに「設計判断」と「既知の制約」を記録する**: 逸脱・簡略化した箇所を理由付きで残す習慣。`fable-projects/README.md` の該当セクションが手本。
5. **予約ロジックの共通化**: user/adminで重複している「バリデーション→重複チェック→insert/update」を `lib/reservations.ts` に切り出す（自分のCLAUDE.mdの規約通りに）。
6. **軽微な掃除**: 空ファイル `{` の削除、`Claude.md`/`CLAUDE.md` の統合、予約時の `max_capacity` バリデーション追加。

## 7. fable（AI）の実力評価

**総評: 「設計書を渡して実装させる」タスクにおいて、コード生成だけでなく設計レビューまで行う実務水準に近い出力。ただし明示的に指示しない限りテストは書かず、コンポーネント分割の規律も完全ではない。**

### 強み（客観的根拠付き）

- **設計書の欠陥を自主的に発見・補正する**: 最も価値が高い能力。RLSの3補正（未ログインメール漏洩・admin更新の静的失敗・role自己昇格）は設計書に書かれておらず、セキュリティレビューに相当する働き。
- **エッジケースの網羅性**: 復元対象同士の相互重複検査、定員減少後の既存予約、境界接触（半開区間）の明示など、指示されていない境界条件を自ら潰している。
- **静的品質**: tsc/ESLintエラー0（実測）。型のジェネリクス注入・strict準拠も一貫。
- **説明責任**: 全ての逸脱・制約・判断がREADMEとコードコメントに記録され、後からトレース可能。
- **速度**: Phase1全機能+スキーマ+ドキュメントを1日で実装（コミット `95d03b9` と修正 `5c320e0` が同日 2026-06-12）。
  - 対比: 自作版は2026-01-09〜2026-06-08の約5ヶ月・138コミット（git履歴実測）。
  - 解釈上の注意: 自作版は学習しながらの実装であり（要件定義書のPhase1見積り50時間も学習込み）、純粋な速度比較として読むのは不公平。ここで測れるのは「AIは学習コストを持たない」という当然の差にすぎない。

### 弱み（客観的根拠付き）

- **テストを自発的には書かない**: 純粋関数（`lib/reservations.ts` 等）というテスト容易な対象がありながらゼロ。「動作確認チェックリスト」で代替しており、品質保証の自動化は指示待ち。
- **コンポーネントが肥大する**: `ReservationManager.tsx` 697行。機能を1ファイルに足し込む傾向があり、分割の規律は人間のレビューが必要。
- **UI一貫性の詰めが甘い**: Toastを自作しながら `alert()`/`confirm()` が10箇所以上残存。
- **確実性より互換性を選ぶ**: 重複防止のDB制約を「用意はするがコメントアウト」にした。本番運用なら有効化すべき判断を利用者に委ねている。

### 使いどころの示唆

fableの出力は「たたき台」ではなく「レビュー対象になる水準の初版」。ただし **(1) テスト、(2) コンポーネント分割、(3) 本番向けの堅牢化（DB制約など）** は明示的に要求しないと出てこないため、依頼時にスコープへ含めるのが効果的。

## 8. 両者共通の改善課題

1. **自動テストの導入**（両者スコア1）: まず純粋関数（重複判定・日時変換）にVitestで単体テストを入れるのが最小コスト・最大効果。次にPlaywrightで予約フローのE2E。
2. **大型コンポーネントの分割**: 両者とも予約管理が700行前後。フォーム・テーブル・モード管理の3分割が目安。
3. **通知UIの統一**: alert/confirm依存（自作は全面、fableは混在）をToast+確認モーダルに統一。テスト自動化の前提にもなる。
4. **重複防止のDB層担保**: アプリ層チェックはレースコンディションをすり抜けうる。fableが用意した `EXCLUDE USING gist` 制約（`schema.sql:288-303`）を両環境で有効化する。
